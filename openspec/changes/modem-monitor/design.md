## Context

См. `proposal.md` — Why. Здесь только то, что формирует подход.

Наблюдения с реального железа, на которых построен весь дизайн:

```
Машина A (Huawei):
  /sys/bus/usb-serial/drivers/option1/ -> ttyUSB0, ttyUSB1, ttyUSB2
      все три от ОДНОГО usb-устройства 3-1
      3-1: 12d1:1001 "HUAWEI Technology / HUAWEI Mobile", bNumInterfaces=3
      iSerial ПУСТОЙ
  /dev/ttyUSB* -> root:<группа>, у процесса нет ни чтения, ни записи
  /run/udev отсутствует (контейнер)

Машина B (SIM800):
  /sys/bus/usb-serial/drivers/ch341-uart/ -> по одному ttyUSB на модем
      посторонних устройств на этом драйвере сейчас нет
```

Ключевые ограничения, вытекающие отсюда:

- Один физический Huawei = три порта; на AT отвечают не все, и незапрошенные сообщения приходят не на любой.
- Пустой `iSerial` означает, что два одинаковых свистка неразличимы средствами USB. Идентичность железа берётся только из IMEI.
- `option1` биндится только к известным WWAN-устройствам, поэтому порт на нём — почти достоверно модем. `ch341-uart` — универсальный мост, за ним может быть что угодно, а VID:PID (`1a86:7523`) описывает мост, не модуль.
- Отсутствие `/run/udev` делает ненадёжным мониторинг hotplug через udev.
- SIM-карты в роуминге: любой исходящий трафик платный, входящие SMS и отклонение вызова — бесплатны.

## Goals / Non-Goals

**Goals:**

- Один процесс, один event loop, никаких внешних брокеров и БД.
- Ни одна команда, стоящая денег, не может быть выполнена — не по соглашению, а конструктивно.
- Ни одна автоматическая ветка не может привести SIM в состояние PUK.
- Полученная SMS не теряется из-за недоступности Telegram.
- Вариативность семейств модемов сосредоточена в одном явном контракте, а не размазана условиями по коду.
- Наблюдаемость достаточна, чтобы ответить на вопрос «почему эта SIM не принимает SMS у этого оператора».

**Non-Goals (уровня дизайна, дополняют non-goals проекта):**

- Устойчивость к падению процесса ровно посреди приёма многочастной SMS — сознательно не обеспечивается (см. D8).
- Персистентное состояние рантайма — его нет вообще (см. D3, D11).
- Горизонтальное масштабирование, несколько инстансов на один набор модемов.
- Абстракция над транспортом (TCP-to-serial, MQTT-шлюзы) — только локальные последовательные порты.

## Decisions

### D1. Обнаружение двухступенчатое: дешёвый фильтр, затем probe

```
  ступень 1 -- ФИЛЬТР (sysfs, порты не открываются)
    обойти driver allowlist из settings.json
    сгруппировать порты по родительскому USB-устройству
    -> кандидаты: [(usb_path, [ports...], vid:pid)]
                        |
  ступень 2 -- PROBE (открывает порт, говорит AT)
    ATE0 -> AT -> ATI / AT+CGMM
      нет ответа        -> NOT_A_MODEM, в негативный кэш
      "SIM800..."       -> Sim800Behavior
      "E1750/E1550..."  -> HuaweiBehavior
      ответ есть, но не опознан -> GenericAtBehavior
```

Почему не только фильтр по драйверу: для `ch341-uart` он не отвечает на вопрос «модем ли это». Почему не только probe всех `/dev/tty*`: это ровно то, чего требовалось избежать — стучаться AT-командами в посторонние UART-устройства.

Отвергнуто: хардкод «`option1` = модем, `ch341-uart` = SIM800». Работает сегодня, ломается в тот день, когда в машину воткнут любой другой CH340-девайс.

### D2. Роль порта определяется пробой, а не индексом

У Huawei нельзя опираться на «ttyUSB1 — это PCUI»: нумерация зависит от порядка подключения и количества модемов. Стратегия получает список портов устройства, пробует каждый и выбирает управляющий — тот, что отвечает на `AT` и на котором успешно включаются нотификации. У однопортовых устройств шаг тривиален.

### D3. Три слоя идентичности, всё соответствие — в RAM

```
+-----------------+--------------------+---------------------+------------------+
| слой            | источник           | стабильность        | назначение       |
+-----------------+--------------------+---------------------+------------------+
| USB-путь        | sysfs: 3-1:1.0     | до перевтыка        | discovery,       |
|                 |                    | ttyUSB* плавают     | какой порт открыть|
+-----------------+--------------------+---------------------+------------------+
| модем (железо)  | AT+CGSN -> IMEI    | навсегда            | "пропал/появился",|
|                 | ATI / AT+CGMM      |                     | выбор стратегии  |
+-----------------+--------------------+---------------------+------------------+
| SIM (логика)    | AT+CCID -> ICCID   | пока не вынули      | КЛЮЧ настроек,   |
|                 |                    |                     | chat_id, история |
+-----------------+--------------------+---------------------+------------------+
```

Настройки ключуются по ICCID: SIM переставили в другой модем — уведомления по-прежнему уходят в свой чат. `AT+CCID` читается до ввода PIN, поэтому цепочка «узнали ICCID → нашли PIN в настройках → разблокировали» замыкается без курицы и яйца.

Соответствие «модем ↔ ICCID» **не сохраняется на диск**: оно восстанавливается опросом железа при каждом старте, а историческая связка остаётся в `events.jsonl`, где каждая запись несёт и IMEI, и ICCID.

Отвергнуто: `iSerial` как идентификатор — у 12d1:1001 он пуст; имя `ttyUSBn` — плавает.

### D4. Reconciler вместо подписки на hotplug-события

```
  каждые N секунд                          ошибка чтения порта (ENODEV)
        |                                              |
        v                                              v
  scan sysfs по allowlist                     сессия умерла
        |                                              |
        +--------------> [ RECONCILER ] <--------------+
                               |
        +----------------------+----------------------+
        v                      v                      v
   появился -> spawn    пропал -> дебаунс      FAULT -> backoff restart
                        -> GONE
```

Причины: `/run/udev` отсутствует; о пропадании модема практически всегда раньше сообщает ошибка чтения, чем uevent; сверка состояний идемпотентна и самовосстанавливается после любого пропущенного события.

Дебаунс перед объявлением `GONE` обязателен: SIM800 на USB просаживает питание при передаче и самопроизвольно переподключается. Без дебаунса Telegram захлебнётся уведомлениями «пропал / появился».

Отвергнуто: `pyudev` monitor — лишняя зависимость, которая в контейнере без udevd может не работать, и всё равно не отменяет обработку ошибок чтения.

### D5. На порт — одна сессия: единственный reader и очередь команд

```
+------------------ AtSession (один экземпляр на порт) ----------------+
|                                                                     |
|  Queue<Command> --> [dispatcher] --write--> serial                   |
|                          ^                    |                     |
|                          |                    v                     |
|                     Future.set_result <-- [reader, построчно]        |
|                          ^                    |                     |
|                          |                    v                     |
|                     +--------- [classifier] ---------+               |
|                     |                               |               |
|              часть ответа команды          незапрошенное:            |
|              (до OK / ERROR / +CME ERROR)  RING, +CLIP, +CMTI,       |
|                                            ^RSSI, ^MODE, ^BOOT       |
|                                                   |                 |
|                                                   v                 |
|                                               EventBus              |
+---------------------------------------------------------------------+
```

Инварианты: ровно одна команда in-flight; `ATE0` в начале, чтобы не разбирать эхо; незапрошенная строка может прийти посреди ответа на команду и обязана быть распознана там же; у каждой команды свой таймаут (`AT+COPS=?` — десятки секунд, `AT+CSQ` — секунда).

Отвергнуто: наивное «записал — прочитал ответ». Ломается на первом же `RING`, пришедшем между записью и чтением.

### D6. Стратегии семейств, фабрика по результату probe

Поведенческий паттерн (Strategy с элементами Template Method для последовательности инициализации). Вариативность сосредоточена ровно в этих точках:

```
                  ModemBehavior (абстрактный)
     +-------------------------------------------------+
     | select_control_port(ports)   роль порта         |
     | init_sequence()              Template Method    |
     | configure_notifications()    CNMI / CLIP / ^CURC|
     | parse_unsolicited(line)      -> Event | None    |
     | read_signal() -> dBm         CSQ vs ^RSSI push  |
     | read_registration()          CREG + CGREG       |
     | read_operator()              COPS               |
     | read_pin_attempts() -> int|None                 |
     | read_sms_storage()           CPMS               |
     | recovery_steps()             лестница           |
     +-------------------------------------------------+
             ^                            ^
     HuaweiBehavior                Sim800Behavior
     3 порта, probe роли           1 порт, автобод
     ^RSSI приходит сам            поллинг CSQ
     ^BOOT / ^SIMST                нет ^-событий
     AT^CPIN? (формат пляшет)      AT+SPIC
     AT^RESET доступен             только AT+CFUN=1,1
```

Фабрика опирается на ответ `ATI`/`AT+CGMM`, а VID:PID использует лишь как подсказку для порядка попыток. Причина: у SIM800 за мостом CH340 VID:PID принадлежит мосту и о модуле не говорит ничего. Значит нужен минимальный generic-AT режим, достаточный чтобы задать `ATI` и только потом выбрать стратегию.

### D7. Только PDU-режим; части склеиваются сырыми и декодируются один раз

`AT+CMGF=0` для всех семейств. В текстовом режиме модем не отдаёт UDH — нельзя узнать ни `ref`, ни `total`, ни `seq`, то есть многочастное сообщение принципиально не собрать.

Декодирование каждой части по отдельности ломается минимум четырьмя способами:

```
[1] UCS2, суррогатная пара:  "😀" = D8 3D DE 00
    граница между D8 3D | DE 00 -> обе половины невалидны
[2] UCS2, нечётная граница:  UDH с 16-битным ref = 7 октетов,
    на текст 133 октета -- нечётно, половина символа уезжает дальше
[3] GSM7, escape:  "€" = 1B 65, граница между ними ->
    висячий ESC в одной части, буква "e" в другой
[4] GSM7, fill-биты: UDH = 6 октетов = 48 бит, септеты должны
    начинаться с бита 49 -> надо пропустить 1 бит, иначе весь
    текст сдвинут
```

Правило: собрать сырьё в порядке `seq` (для GSM7 — распакованные септеты, для UCS2 — байты), декодировать один раз. Порядок берётся из UDH, а не из порядка прихода.

### D8. Сборка в памяти, память SIM освобождается сразу

```
  +CMTI: "SM",5
      |
      v
  AT+CMGR=5 -> PDU hex
      |
      v
  разбор заголовка: sender, timestamp, UDH{ref,total,seq}, encoding, payload
      |
      +--> AT+CMGD=5              память SIM освобождается НЕМЕДЛЕННО
      |
      v
  RAM: groups[(iccid, sender, ref, total)][seq] = payload
      |
      +-- собраны все total -> склейка сырья -> decode ->
      |        events.jsonl {"type":"sms", ..., "raw":[pdu...]} -> telegram
      |
      +-- таймаут ~10 мин -> events.jsonl {"type":"sms","incomplete":true,
                                           "missing":[3], ...} -> telegram
```

Trade-off принят осознанно: падение процесса ровно между чтением частей и завершением сборки теряет сообщение. Вероятность низка, а выигрыш — отсутствие персистентного состояния и мгновенное освобождение памяти SIM, которая является вероятной причиной пропажи SMS.

В **завершённую** запись лога кладутся сырые PDU всех частей. Парсер PDU пишется руками, первые версии будут ошибаться; имея сырьё, историю можно перепарсить, не имея — испорченные тексты испорчены навсегда. Ротации нет, объём не ограничивает.

Отвергнуто: держать части на SIM до полной сборки — при недосборе память забивается и приём встаёт; писать каждую часть в лог отдельной записью — усложняет чтение истории без реальной выгоды при принятом trade-off.

### D9. Ключ группы сборки включает отправителя и имеет таймаут

`assembly_key = (iccid, sender_address, ref, total)`. Восьмибитный `ref` имеет всего 256 значений и переиспользуется, поэтому без таймаута две разные SMS от одного отправителя рано или поздно склеятся в одну. Группа живёт ограниченное время, затем закрывается как `incomplete`. Повторно пришедший `seq` игнорируется — части индексируются, а не дописываются.

### D10. Память SIM — под наблюдением, и это функциональное требование

`AT+CPMS?` попадает в регулярный опрос и на страницу статуса. При инициализации выполняется `AT+CMGL` и выгребается всё накопившееся, пока приложение не работало. Иначе старые сообщения продолжают занимать память, а заполненная память даёт ровно тот симптом, который наблюдается: модем в сети, сигнал есть, ошибок нет, SMS не приходят.

### D11. PIN-guard: пробуем только при 3+ попытках; счётчик и есть latch

```
  AT+CPIN?
     +-- READY --------------------------------> дальше (обычный случай:
     |                                           у большинства SIM PIN снят)
     +-- SIM PUK / PUK2 ----------------------> FAULT_PUK, alert,
     |                                           не отправляется ничего
     +-- SIM PIN
            |
            v
     read_pin_attempts()        бесплатно, попытку не тратит
            |
   +--------+----------+----------------+-------------------+
 >= 3      <= 2      None (не читается)  PIN не задан
   |        |          |                  |
   v        v          v                  v
 ОДНА     ОТКАЗ      ОТКАЗ            WAITING_PIN
 попытка  + alert    + alert          (ждём ввода в UI)
```

Персистентный latch не нужен, потому что счётчик хранится на самой SIM:

```
  попытка 1: счётчик 3 -> неверный -> счётчик 2
  рестарт:   счётчик 2 -> ОТКАЗ
  рестарт:   счётчик 2 -> ОТКАЗ        ... всегда
```

Цикл «ресет → попытка → ресет → попытка» физически невозможен, файла состояния для этого не требуется. Нечитаемый счётчик приравнивается к запрету: автономность отдельного модема важнее, чем риск убить SIM.

Обхода guard в UI нет. Восстановление после неверного PIN — физическое: SIM вставляется в телефон, PIN исправляется там, счётчик возвращается к 3.

Отвергнуто: разрешать одну попытку при нечитаемом счётчике с записью факта попытки на диск до отправки команды. Даёт автономность, но возвращает файл состояния и тратит попытку.

### D12. Ровно два файла, оба в формате из требований

```
  settings.json   намерения человека, правится через UI, права 0600
    auth{password}, telegram{token}, admin_chat_id,
    drivers[], intervals{}, sims{ iccid -> {label, msisdn, pin,
                                            plmn, chat_id} }

  events.jsonl    история, append-only, БЕЗ ротации
    sms | call | modem_up | modem_gone | sim_absent | sim_unknown |
    pin_guard | puk_locked | no_service | scan_result | ...
```

`settings.json` перезаписывается атомарно (запись во временный файл в том же каталоге, `fsync`, `rename`), иначе одновременная правка из UI и падение процесса дают обрезанный конфиг. `events.jsonl` — построчный append.

Оба места, читающие историю, обязаны читать **с конца через seek**: страница истории (последние N записей) и восстановление после старта. Файл за годы вырастет до гигабайтов, и полного прохода по нему не должно быть нигде в коде.

### D13. Входящий вызов: окно ожидания CLIP, затем отклонение

```
  t=0.0  RING                            <-- номера здесь нет
  t=0.1  +CLIP: "+7999...",145,...       <-- номер здесь
  t=5.0  RING (повтор того же вызова)
```

`RING` открывает окно (порядка двух секунд) в ожидании `+CLIP`; повторные `RING` внутри окна игнорируются; затем вызов отклоняется и формируется ровно одно событие. Без окна номер будет неизвестен, без дедупа один вызов даст четыре уведомления. `AT+CLIP=1` обязателен в последовательности инициализации.

### D14. Платные команды запрещены в транспорте

`AT+CMGS`, `AT+CMSS`, `ATD`, `AT+CGDATA` и подобные отклоняются самим `AtSession` с исключением, не доходя до порта. `ATH` / `AT+CHUP` разрешены — отклонение вызова бесплатно.

Причина: «мы не отправляем SMS» — не стилевое пожелание, а денежное ограничение. Проверка в транспорте делает невозможным случайный расход через будущий рефакторинг или «удобную кнопку» в UI.

### D15. Два канала уведомлений

```
  SMS, входящий вызов        -> chat_id по ICCID из settings.json
  здоровье системы           -> admin_chat_id
    нет SIM, модем пропал, PIN-guard, PUK, нет регистрации
  ICCID известен, но не настроен -> admin_chat_id + приглашение настроить
```

`admin_chat_id` обязателен: у части событий ICCID неизвестен в принципе (модем не отвечает на AT), и адресата у них иначе нет. Последний случай попутно работает как onboarding: вставили новую SIM — пришло «обнаружена RU-...7890, чат не назначен».

Доставка — через очередь с повторами и экспоненциальной задержкой. Telegram не является границей надёжности: событие уже лежит в `events.jsonl`, недоступность Telegram не влияет на приём. Уведомления о входе в состояние дедуплицируются, иначе «нет SIM» будет капать каждый цикл опроса.

### D16. Ручная привязка PLMN; скан — явное действие; автооткат отсутствует

`AT+COPS=1,2,"<plmn>"` при заданной привязке, `AT+COPS=0` если не задана. Скан `AT+COPS=?` не входит в регулярный опрос: он длится десятки секунд и на это время выводит модем из сети, а значит SMS не принимаются. Скан запускается только кнопкой в UI, модем при этом в отдельном состоянии, результат кэшируется в памяти и попадает в лог.

Ручная привязка сама не откатывается: если оператора нет в эфире, модем останется без сети. Watchdog уведомляет об этом в admin-канал, но автоматически на `AT+COPS=0` не переключается — иначе поведение системы перестаёт соответствовать заданному в настройках, причём молча.

### D17. HTTP-сервер в том же процессе; PIN — write-only; метрики открыты

Один процесс, один event loop: страница статуса, API настроек и `/metrics` живут рядом с опросом модемов.

Авторизация символическая — один пароль открытым текстом в `settings.json`. `/metrics` без авторизации, чтобы не усложнять конфигурацию Prometheus; текстов SMS в метриках нет.

PIN никогда не покидает процесс в сторону UI:

```
  GET /api/sims/<iccid> -> {"pin_set": true, "pin_attempts_left": 3, ...}
                            ^^^^^^^^^^^^^^^ значение не отдаётся никогда
  PUT /api/sims/<iccid> <- {"pin": "1234"}  задать
                        <- {"pin": null}    удалить
                        <- {}               не менять
```

Отсюда следствие: сериализация конфига для API отличается от сериализации в файл. PIN маскируется в отладочном эхе AT-команд (`AT+CPIN="****"`) и отсутствует в метриках.

Человеческое имя SIM выносится в info-метрику, а не в метки метрик значений:

```
  mm_sim_info{iccid="8970...", label="Роуминг-МТС-2", msisdn="+7..."} 1
  mm_signal_dbm{iccid="8970..."} -87        <-- только iccid
```

Иначе переименование SIM в UI создаёт новый time series и разрывает графики.

### D18. Имя SIM: автоимя из ICCID плюс пользовательское

```
  ICCID:  8970 1 02 1234567890 4
          ^^^^ ^ ^^
           |   |  +-- эмитент (оператор) -- по таблице, эвристика
           |   +----- код страны (E.118), 7 = RU -- надёжно
           +--------- 89 = телеком

  автоимя:      "RU-...7890"       без настройки, читаемо сразу
  пользователь: "Роуминг-МТС-2"    перекрывает автоимя
```

Последние четыре цифры обычно напечатаны на самой SIM, поэтому автоимя сразу связывает запись в UI с физической картой. Контрольная цифра по Луну проверяется как подсказка «похоже на битый ICCID», но не как отказ — она есть не у всех эмитентов.

### D19. Лестница восстановления, различная по семействам

```
  таймаут / повторяющиеся ошибки
        |
   [1] повтор команды
        |
   [2] переоткрыть порт
        |
   [3] софт-ресет:  Huawei AT^RESET | AT+CFUN=1,1     SIM800 AT+CFUN=1,1
        |
   [4] FAULT + уведомление "нужны руки"
```

У SIM800 лестница короче: один порт на всё, а PWRKEY программно не нажать. Поэтому шаг [4] для него достижим и является нормальным исходом, требующим человека.

## Risks / Trade-offs

- **Падение процесса посреди сборки многочастной SMS теряет сообщение** → принято осознанно (D8); вероятность низка, взамен нет персистентного состояния и память SIM освобождается сразу.
- **Просадки питания SIM800 на USB дают ложные «модем пропал»** → дебаунс перед `GONE` и счётчик переподключений в метриках, чтобы проблема была видна как проблема питания, а не как загадка.
- **Формат `AT^CPIN?` у Huawei различается по прошивкам, счётчик может не распарситься** → `read_pin_attempts()` возвращает `None`, а `None` трактуется как запрет попытки. Ошибка разбора приводит к безопасному отказу, а не к риску PUK.
- **Самописный парсер PDU будет ошибаться** → сырые PDU сохраняются в лог, историю можно перепарсить после исправления.
- **Probe пишет `AT` в устройство, которое может оказаться посторонним** → круг сужен allowlist драйверов, вердикт кэшируется, повторных обращений нет. Открытие CH341-порта дёргает DTR/RTS и способно перезагрузить Arduino-подобную плату; сейчас посторонних устройств на этом драйвере нет, но если появятся — понадобится явный allowlist USB-путей.
- **ModemManager на обычном хосте конкурирует за те же порты** → порты исключаются из его управления правилом udev; иначе диагностика будет крайне запутанной.
- **Нет прав на `/dev/ttyUSB*`** → правило udev или группа; без этого приложение не стартует вообще.
- **Скан сети выводит модем из сети на десятки секунд** → только по явному действию, отдельное состояние, предупреждение в UI.
- **Ручная привязка PLMN может оставить модем без сети навсегда** → watchdog и уведомление; автооткат сознательно не делается (D16).
- **Секреты открытым текстом** → права `0600`, отсутствие в логах, метриках и API-ответах. Пароль UI и тексты SMS (в них бывают одноразовые коды) идут по сети без шифрования — это принято в расчёте на доверенную сеть или туннель.
- **`events.jsonl` растёт неограниченно** → чтение только с конца через seek; полный проход по файлу считается дефектом.
- **Автобод SIM800 удлиняет probe** → перебор короткого списка скоростей с малым таймаутом; скорость можно закрепить в настройках для конкретного USB-пути.

## Migration Plan

Проект новый, миграции данных нет. Порядок внедрения:

1. Транспорт и стратегии на одном Huawei и одном SIM800 — только чтение статуса, без нотификаций. Проверить probe, выбор роли порта, формат `AT^CPIN?` и `AT+SPIC`.
2. Приём SMS в PDU с логом сырья; сверка декодированного текста с телефоном на длинных сообщениях и на сообщениях со спецсимволами.
3. Звонки: проверить, что `RING` и `+CLIP` действительно приходят на обоих семействах.
4. Telegram и `events.jsonl`.
5. Страница статуса, API настроек, `/metrics`.
6. Развёртывание: systemd unit, правило udev на права и на исключение из ModemManager, `settings.json` с правами `0600`.

Откат — остановка сервиса; модемы не остаются в изменённом состоянии, кроме ручной привязки PLMN, которая снимается `AT+COPS=0`.

## Open Questions

Все они проверяются на живом железе и не меняют ни подход, ни спецификации, ни разбивку работ:

- Точный формат ответа `AT^CPIN?` на конкретных прошивках Huawei. До проверки счётчик считается нечитаемым, что безопасно.
- Какие имена хранилищ SMS поддерживает `AT+CPMS` у SIM800 и Huawei (`"SM"`, `"ME"`, `"SM_P"`), и не пишет ли какой-то из них входящие в память модема, а не SIM.
- Реальные интервалы опроса: насколько можно разредить поллинг у Huawei, полагаясь на `^RSSI`, и какой интервал не мешает SIM800.
- Достаточен ли двухсекундный дебаунс `GONE` для самопроизвольных переподключений SIM800 по питанию.
