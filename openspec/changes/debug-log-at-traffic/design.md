## Context

`AtSession` уже принимает `trace: bool = False` и, будучи включённым, пишет `<port> > <command>` перед отправкой и `<port> < <line>` для каждой прочитанной строки в свой логгер `modemmanager.at.session`. Флаг не установлен нигде: в `probe.py` сессия создаётся напрямую `AtSession(self.transport_factory(...))`, в `discovery/reconciler.py` через `Modem`, в `at/recovery.py` — при переоткрытии. Маскировка `at.guard.mask` уже применяется к строке исходящей команды через `_display(...)`, но входящие строки идут в лог как есть.

## Goals

- Обменом на порту можно управлять «включи трассировку и получи полный лог для этого модема», не меняя код.
- Ноль накладных расходов при выключенной настройке (сегодняшнее поведение), в том числе одинаковый объём журнала.
- Секреты не утекают через новый канал.

## Non-Goals

- Отдельный файл трассировки, ротация, JSON-формат — сейчас достаточно `logging.DEBUG` в общий журнал.
- Управление трассировкой на лету (через HTTP или SIGHUP): перезапуск приложения с новой настройкой — приемлемо.
- Трассировка только «этого одного модема»: разбирать по портам предлагается фильтрами в потребителе журнала. Для узкого адресного дебага это дороже, чем стоит.
- Правки логгирования выше уровня сессии (метрики, обнаружение) — сегодня их достаточно.

## Decisions

### Явная настройка, а не «включать при `--log-level=DEBUG`»

Триггер трассировки — отдельный флаг в конфиге (`discovery.at_trace: bool`), а не только уровень логгера. Причины:

- Пользователь может хотеть `DEBUG` из-за одной проблемной подсистемы (например, обнаружения) без десятков тысяч строк обмена в час.
- Трассировка содержит номера, IMEI и служебные ответы модема — при удалённой поддержке имеет смысл включать её сознательно, а не автоматически с общим DEBUG.
- Настройка легко проверяется в тестах.

Альтернатива «включать по логгеру `modemmanager.at.session` → `DEBUG`» отклонена: у логгеров нет способа хранить смысловые уровни включённости, только уровни серьёзности, и подход требует ручного управления в `logging.basicConfig`.

### Одна настройка, применяется ко всем сессиям

Проба, обслуживающая сессия и восстановление создают сессии независимо — но флаг у них должен быть один. Прокидывается он из настроек в:

- `Prober.__init__(trace=...)` → в `_ask_identity` и `_can_control` при создании `AtSession(...)`;
- `Modem.__init__(trace=...)` или создатель сессии в `Modem` — единая точка;
- `RecoverySession`/`ReopenPolicy` — та же переменная.

Альтернатива «включить через глобальный класс-атрибут `AtSession.default_trace`» отклонена: скрытая связка, ломает тесты, требующие двух режимов в одном процессе.

### Маскирование секретов на входящем канале

Сейчас исходящее маскируется в `_display(...)`. Входящее (`<port> < <line>`) сегодня без маски: секретов там обычно нет (модем не эхоит PIN, если `ATE0` уже прошло), но эхо ДО `ATE0` возможно — пробную последовательность инициализации команда с секретом обгоняет крайне редко, однако полагаться на это в диагностическом контракте нельзя.

Решение: пропускать входящую строку через тот же `at.guard.mask` перед логированием. Функция safe для строк без секретов (возвращает вход как есть); стоимость — одно применение регулярки на строку, только при включённой трассировке.

Альтернатива «маскировать только исходящее» отклонена: не соответствует MODIFIED-требованию «эхо команды с PIN».

### Место настройки: `DiscoverySettings`

`at_trace` кладётся в `DiscoverySettings`, потому что оттуда сессии рождаются (проба, реконсиляр). Альтернатива — новый раздел `debug` — избыточна для одной строки. Если потом появятся ещё диагностические переключатели, их логично объединить в свой раздел; сейчас — не время.

## Risks / Trade-offs

- Объём журнала при включении → регулярный пуш-обмен Huawei (`^RSSI`, `^HCSQ`) может писать десятки строк в минуту на модем. Митигация: трассировка выключена по умолчанию; в документации/`README` явно предупредить.
- Гонка «пользователь включил трассировку в конфиге, но забыл `--log-level=DEBUG`» → в журнале ничего нет, ощущение поломки. Митигация: при запуске приложения, если `at_trace=True` и корневой логгер выше `DEBUG`, писать одну строку `WARNING` вида «трассировка AT включена в настройках, но уровень журнала — INFO».
- Утечка секретов через строки, не проходящие через `mask` (например, если модем прислал что-то неожиданное с PIN в середине строки) → сегодня `mask` работает только по регулярке в начале строки. Митигация: в рамках этого изменения — не расширять `mask`, только применить его; отдельно поднять расширение маски в будущем, если реально прилетит такая строка. Для входящего эха AT-команды с PIN текущей маски достаточно.

## Migration Plan

- Deploy: обновить код, добавить `discovery.at_trace: false` в существующий `settings.json` не требуется — поле опциональное, по умолчанию `false`.
- Rollback: снять правки; `AtSession.trace` остаётся мёртвым флагом, поведение не меняется.
- В `README` описать: как включить и что содержит трассировка, ссылка на предупреждение об объёме.
